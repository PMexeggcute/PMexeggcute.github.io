0.2 静态库与动态库

多个 .o 打包起来就是库。两种：

静态库 动态库
文件名 libfoo.a libfoo.so
链接时机 编译时 运行时
代码在哪 复制进可执行文件 单独一个文件，运行时加载
可执行文件大小 大 小
改库要不要重编程序 要 不要

Linux 的动态库版本管理：一个文件，三个符号链接。

假设有一个 libfoo 版本 1.2.3，装到系统里是这样：

  • libfoo.so.1.2.3 —— 真实文件。
  • libfoo.so.1 —— 主版本号。并存的多个版本靠它区分：libfoo.so.1 和 libfoo.so.2 可以同时装。
  • libfoo.so —— 只在你编译时有用（-lfoo 找的就是它），运行时不看它。

这里埋了一个巨大的坑，见 §0.4 和 §10.5：符号链接一旦被破坏，整套机制就崩了。

为什么不把 libfoo.so 也做成真实文件？因为那样就没法”同时存在多个版本”了 —— 一个目录下只能有一个叫 libfoo.so 的文件。

0.4 CMake 是什么

先看不用 CMake 的痛

一个稍大的 C++ 项目，手写 Makefile 会遇到：

  • 跨平台：Windows / Linux / macOS 的编译器和路径规则不同，要写三套
  • 依赖管理：项目依赖 zlib，但 zlib 可能装在 /usr/lib、/usr/local/lib，也可能是自己编的，路径要能自动找到
  • 可移植性：库的版本不同，要用不同的宏、不同的链接参数
  • 构建配置：Debug / Release 要产出不同的优化选项

Makefile 能解决，但会写得非常长且难以维护。

CMake 的定位

CMake 不是编译器，也不是构建工具，它是”构建文件的生成器”。

你只需要写一份平台无关的 CMakeLists.txt，CMake 负责把它翻译成当前平台能用的构建文件。

第 1 部分：原理——四个根本问题

1. 什么是交叉编译

在 A 类机器上编译出能在 B 类机器上运行的程序。

  • 宿主 / 构建机（host）：执行编译的地方
  • 目标机（target）：运行产物的地方

术语提示：autoconf 体系里有 build / host / target 三个词，容易混淆。在”不构建编译器本身”的场景下，build == host == 你的编译机，target == 目标机。本文统一用”宿主”和”目标”。

为什么需要它？

  1. 算力：嵌入式设备编译一个稍大的项目要几十分钟到几小时，x86 服务器几分钟就够。
  2. 环境：目标机通常没有完整的 gcc/cmake/开发库。
  3. 一致性：CI 跑在 x86 服务器上，不可能为每个架构准备一台原生构建机。

为什么它难？

因为整个工具链的默认行为都建立在**”我在本机”**这个假设上：编译器去 /usr/include 找头文件、链接器去 /usr/lib 找库、pkg-config 读本机的配置、CMake 按本机架构做判断。

交叉编译的本质，就是系统性地打破这个假设。

2. 四个根本问题

任何交叉编译方案，无论用什么构建系统，都必须回答四个问题。这是全文的骨架：

# 问题 手段 决定什么
Q1 用谁的编译器？ 工具链前缀 / CMAKE_TOOLCHAIN_FILE 产物的架构
Q2 用谁的头文件和库？ sysroot 编译能否通过
Q3 怎么保证找依赖时不跑到宿主上？ CMAKE_FIND_ROOT_PATH_MODE_* / PKG_CONFIG_* 依赖是否正确
Q4 运行时怎么找到 .so？ SONAME / RPATH / LD_LIBRARY_PATH 产物能否跑起来

★ 最重要的一句话

Q1–Q3 决定”能不能编译出来”，Q4 决定”编译出来的东西能不能跑”。这两件事完全独立。

一个交叉编译产物可以做到：架构 100% 正确、编译零警告、链接零错误、所有常规检查全绿 —— 然后在目标机上启动即失败。

因为 Q1–Q3 只管到”链接完成”这一刻。而 .so 是运行时才加载的，那一刻发生在目标机上，跟你的构建环境已经没关系了。

这是交叉编译里最容易被忽略、也最难发现的一类问题。第 3 部分的坑四专门讲它。

3. Q1：用谁的编译器

3.1 命名规则

GNU 工具链的命名是：

例：aarch64-linux-gnu-gcc

段 值 含义
arch aarch64 目标 CPU 架构（ARM 64 位）
vendor linux 厂商，通常是 linux 或 none
os gnu 目标 OS/ABI 是 glibc
tool gcc 工具本身

aarch64-linux-gnu- 这一段叫 prefix（前缀）。装好工具链后会得到一整套：-gcc、-g++、-ld、-as、-objdump、-nm、-readelf……

常见困惑解决：aarch64 和 arm64 是同一个东西。前者是 GNU 的叫法，后者是 Apple/LLVM 的叫法。Ubuntu 的 dpkg --print-architecture 在 ARM64 上输出 arm64，而 uname -m 输出 aarch64。这俩对不上不是错误。

最朴素的想法是 CC=aarch64-linux-gnu-gcc cmake ..。

比”编译失败”危险得多：编译失败你立刻知道；这个你什么都不知道。

具体会碎在四个地方：

  1. 架构判断错 —— 上面已经演示。
  2. try_run() 会失败 —— CMake 大量用”编译并运行一小段代码看结果”来探测特性。aarch64 的可执行文件在 x86_64 宿主上根本执行不了。CMAKE_CROSSCOMPILING=TRUE 时 CMake 会自动跳过实际执行，FALSE 时它会去执行然后得到垃圾结果或报错。
  3. 库搜索路径没变 —— find_library() 照样去宿主的 /usr/lib/x86_64-linux-gnu 找，拿到 x86_64 的 .so。
  4. pkg-config 没变 —— 照样读宿主的 .pc 文件，吐出一堆宿主路径。

所以需要一个在 project() 之前就把这些探测结果全部钉死的机制。

3.4 ★ CMAKE_SYSTEM_NAME 是开关

CMAKE_SYSTEM_NAME 比”设置编译器”重要得多。

CMake 内部有个变量 CMAKE_CROSSCOMPILING，表示”当前是否在交叉编译”。而这个变量只有在 toolchain file 里设置了 CMAKE_SYSTEM_NAME 才会变成 TRUE。

一旦为 TRUE，CMake 会自动：

  • 跳过 try_run() 的实际执行（改为只编译不运行）
  • 激活下文的 CMAKE_FIND_ROOT_PATH 重定向规则
  • 改变一系列默认行为

很多人第一次写 toolchain file 只设了编译器，然后困惑于”为什么还是不对”—— 就卡在这一行。

4. Q2：用谁的编译产物依赖

4.1 sysroot 是什么

交叉编译有个危险：编译器默认去 /usr/include 找头文件。这会让你把宿主的头文件和 .so 编进目标架构的程序。

sysroot 的思路：准备一整套目标机的根文件系统，放在宿主的一个目录里，告诉编译器”把这里当成目标的 /“。

4.2 ★★ --sysroot 不重写绝对路径

这是全文最重要的一条规则，请务必理解透。

--sysroot 只影响 -L 搜索路径和默认搜索目录，不会重写显式写在命令行上的绝对路径。

对比这两种写法：

写法一里 -L/usr/lib 会被改写成 /sys/usr/lib；写法二里 /usr/lib/libz.so 原样使用 —— ld 打开的是宿主的那个文件。

这个规则的后果：

情况 结果
宿主文件是错误架构 ld 报 file in wrong format / incompatible target —— 失败，你立刻知道
宿主文件恰好是正确架构 ld 静默链接成功 —— 产物里记下这个名字，目标机上未必有它

第二种情况是灾难性的：不报错、不警告，只在部署时炸。 第 3 部分的坑四就是它。

命令行的对照见 §9（实验二），那里有可复现的完整输出。

4.3 sysroot 从哪来

三种来源：

  1. 从目标机直接拷贝 —— rsync 或 tar 整个 /（排除 /proc /sys /dev）。最真实，但体积大。
  2. 芯片厂商的 SDK/BSP 提供 —— 通常是预打包好的。
  3. 从 deb 包解出 —— dpkg -x 或 apt-get download 后解压，只取需要的部分。适合补齐缺失的文件。

⚠️ 用第 1 种方式时，必须用能保留符号链接的工具。见 §10.5。

5. Q3：怎么保证找依赖时不跑到宿主上

有了编译器和 sysroot，还剩一个问题：构建系统里的 find_package() / find_library() / pkg-config 怎么知道该去哪找？

5.1 CMAKE_FIND_ROOT_PATH 与四个 MODE

CMake 提供了一套”查找根目录”机制。CMAKE_FIND_ROOT_PATH 是一个前缀列表，find_* 命令会在每个前缀下再搜一遍。

但只有前缀不够 —— find_program 和 find_library 的需求是相反的：

  • find_program（找可执行程序）：要宿主的。构建过程中要运行 cmake、python3、各种代码生成器，这些必须是宿主原生的，否则根本执行不了。
  • find_library（找库）：要目标的。

所以 CMake 给了四个独立开关：

值 含义
NEVER 忽略 CMAKE_FIND_ROOT_PATH，按正常路径找
ONLY 只在 CMAKE_FIND_ROOT_PATH 下找
BOTH 先按正常路径找，再在 CMAKE_FIND_ROOT_PATH 下找

MODE_PROGRAM=NEVER 是必须的。 另外三个按项目需要配。

MODE_PACKAGE=BOTH 是一个有意的取舍：它让 Config 模式的 find_package() 能搜到宿主上的包。有些库只装在宿主的 /usr/local 下（比如手动编译安装的），设成 ONLY 就找不到了。但代价是 —— 宿主上找到的 Config 文件里那些绝对路径，会成为静默的链接错误来源（§4.2 + 坑四）。

5.2 回顾：find_package 的两种模式

回到 §0.4 讲过的：

  • Module 模式（FindXXX.cmake）：内部用 find_library() / find_path()，会被上面的 MODE 重定向。交叉编译友好。
  • Config 模式（XXXConfig.cmake）：内部是打包时写死的绝对路径，不会被重定向。

所以 MODE_LIBRARY=ONLY 拦不住 Config 模式的包。 它只管 find_library()，管不到已经在配置文件里写好的绝对路径。

5.3 pkg-config

pkg-config 从 .pc 文件里读 -I / -L / -l 并拼成编译参数。默认它读宿主 /usr/lib/pkgconfig，交叉编译必须干预：

环境变量 作用
PKG_CONFIG_SYSROOT_DIR 给输出的 -I/-L 路径加上前缀
PKG_CONFIG_LIBDIR 替换（而非追加）.pc 文件的搜索路径

两个都要设。 只设前者，.pc 文件本身还是从宿主读的，版本可能不对；只设后者，路径里不带 sysroot 前缀，-I/usr/include 依然指向宿主。

注意是 set(ENV{...}) 不是 set(...)。这俩是环境变量，必须真的写进子进程的环境里。写成 set(PKG_CONFIG_LIBDIR ...) 只是定义了一个 CMake 变量，pkg-config 根本看不到。

6. Q4：运行时怎么找到 .so

6.2 动态加载器的搜索顺序

运行时，ld.so（动态加载器，也叫 program interpreter）按固定顺序查找 DT_NEEDED 里的库：

  1. DT_RPATH（已废弃；仅当没有 DT_RUNPATH 时才生效）
  2. 环境变量 LD_LIBRARY_PATH
  3. DT_RUNPATH
  4. /etc/ld.so.cache（由 ldconfig 生成）
  5. 默认目录 /lib、/usr/lib（以及多架构的 /lib/<triple> 等）

前三个是你可以控制的。默认目录和 cache 由目标机决定，你在构建期无法影响。

用 -Wl,-rpath,<dir> 把搜索路径写进产物：

$ORIGIN 是产物自身所在的目录。用它做”相对自身定位”是发布包最常用的手法：

这样整个目录树可以随便挪位置、随便复制到别的机器，不需要设 LD_LIBRARY_PATH。

RPATH 和 RUNPATH 的区别：RPATH 是旧机制，优先级高于 LD_LIBRARY_PATH；RUNPATH 是新机制（--enable-new-dtags，现代工具链默认），优先级低于 LD_LIBRARY_PATH。

实践上：用 RUNPATH。它允许用户用 LD_LIBRARY_PATH 覆盖，调试时方便得多。

如果一个产物既没有 RPATH 也没有 RUNPATH，它在目标机上就完全依赖 LD_LIBRARY_PATH 和系统默认路径。 这是坑四的直接原因之一。

6.4 -rpath-link 和 -rpath 不是一回事

链接一个可执行文件时，ld 需要解析直接依赖。但如果直接依赖的 .so 自己还有依赖（间接依赖），ld 也需要能找到它们才能完成符号解析。

-Wl,-rpath-link,<dir> 就是告诉 ld 去这些目录找间接依赖：

-rpath -rpath-link
生效时机 运行时 链接时
是否写进产物 是（DT_RPATH/DT_RUNPATH） 否
解决什么 运行时找不到库 链接时找不到间接依赖

-rpath-link 有个边界：它只对”以合法 ELF 存在的文件”有效。 如果被 NEEDED 的是个文本文件，ld 照样抓瞎，而且会报一个跟 rpath-link 看起来毫无关系的错误。这就是 §10.5 那个坑。

14. 四个经典坑

这四个坑覆盖了交叉编译最常见的四类问题，每一个都对应四个根本问题中的某一个。

坑一：sysroot 不完整，报错点离根因十万八千里

现象：find_package(spdlog REQUIRED) 失败，报找不到包。但 spdlogConfig.cmake 明明在 sysroot 里躺着。

根因：那个 config 文件 include() 的某个依赖文件里，引用了一个 sysroot 中不存在的路径，触发了校验宏的 FATAL_ERROR。报错信息指向的是那个引用，不是缺失的目录。

对应：Q2（sysroot）

教训：sysroot 不完整时，报错点往往离根因很远。

「find_package 失败」不一定等于「包没装」，可能是：

  • 包在，但它依赖的某个 cmake 文件引用的路径不存在
  • 包在，但版本不匹配
  • 包在，但它的 Config 文件里的路径是宿主的

一个有用的信号：很多库的 config 文件里都有类似 set_and_check() 的宏 —— 它的作用就是”检查这个路径存在，不存在就报错”。看到它报错，第一反应应该是”某个路径不存在”，而不是”这个库有问题”。

坑二：符号链接被拍平成文本文件

现象：链接时报 file format not recognized，或运行时报找不到库。

对应：Q2（sysroot）

根因：Linux 动态库用符号链接做版本管理（§0.2），而 Windows 文件系统 API 和很多解压工具不支持 Linux 符号链接，会把它变成一个内容是目标路径的文本文件。

验证（见 §10.5）：

为什么这个坑特别隐蔽：-rpath-link 也会去打开这个文件，读到文本而非 ELF，然后报一个跟 rpath-link 看起来毫无关系的错。

教训：sysroot 必须用能保留符号链接的工具传输。 用 WSL 里的 tar/rsync，或者管理员权限的解压工具。

坑四 ★：库”链接成功”但产物里没有

现象：交叉编译全部通过，产物架构验证 100% 干净。拿到目标机上启动即失败：

对应：Q4（运行时）—— 但根因在 Q3

排查过程：

根因（完整的因果链）：

  1. 某个第三方库用 Config 模式 导出（§0.4）
  2. 它的 Targets.cmake 里写的是 ${_IMPORT_PREFIX}/lib64/libxxx.so.9.8.3296 这样的绝对路径
  3. _IMPORT_PREFIX 由配置文件位置推算，最终指向宿主上的某个真实路径
  4. 链接命令里就出现了这个绝对路径
  5. --sysroot 不重写显式绝对路径（§4.2），ld 打开了宿主上的那个文件
  6. 宿主上的这个文件恰好是正确架构，于是静默链接成功
  7. 产物的 DT_NEEDED 记下了 libxxx.so.9，但没有 RPATH
  8. sysroot 里没有、发布包里没有、目标机上也没有 ⇒ 启动失败

为什么 MODE_LIBRARY=ONLY 没拦住？ 因为它只管 find_library()。这里的路径来自 Config 模式的 imported target，走的是 MODE_PACKAGE，而它通常是 BOTH。

为什么所有常规检查都是绿的？

检查 结果 为什么漏掉
架构验证 46 个 aarch64，0 个 x86_64 产物确实是 aarch64，没问题
构建日志 无错误无警告 ld 确实成功打开了文件
链接 成功 文件架构匹配
readelf -d 有 DT_NEEDED 只说明”需要它”，不说明”有它”

没有任何自动化检查会告诉你”你链接了一个宿主上的库”。

教训：

  1. “编译通过”和”能运行”是两件独立的事（§2）。
  2. 必须做第三层验收（§13）：把 DT_NEEDED 逐条列出来，对着目标机一个一个核。
  3. 绝对路径链接是静默的。 它不警告，不失败，只在部署时炸。

处理方向（取决于目标机是否已装该库）：

  • A. 随包下发 —— 把这个 .so 放进发布包，并把它的目录加进运行时的 LD_LIBRARY_PATH
  • B. 目标机预装 —— 在目标机上装好这个库

选哪条取决于库的体积和部署方式。大的库（几十 MB）随包下发会显著增加发布包体积。

改了什么 要做什么
业务代码 增量编译即可
CMakeLists.txt 增量即可，构建系统会重新 cmake
工具链文件 / CMAKE_SYSROOT 必须全量重建 —— CMake 不跟踪 toolchain 文件内容变化
sysroot 内容（补目录、修软链） 必须全量重建 —— 旧 CMakeCache.txt 里存着上次的查找结果
源码根路径 删掉对应的 build/<pkg>（CMakeCache.txt 记录了源码目录）

这条矩阵很实用。“改了 sysroot 但没清 cache”是一个高频的自我欺骗来源 —— 看起来重新编译了，其实用的还是旧的查找结果。

完整检查清单

编译前

  • 交叉工具链在 PATH 里（aarch64-linux-gnu-gcc --version）
  • sysroot 完整：头文件、.so、cmake/、pkgconfig/ 都在
  • sysroot 里的符号链接是符号链接，不是文本文件（§10.5 的判据）
  • 没有遗留的宿主 CMakeCache.txt
  • 工具链文件里设了 CMAKE_SYSTEM_NAME（§3.4）

编译后

  • 产物架构正确（0 个 x86_64，解释器是 /lib/ld-linux-aarch64.so.1）
  • 依赖探测工程未定义符号为 0（§12）
  • DT_NEEDED 逐条核对目标机可得性（§13 第三层）

部署前

  • 非系统依赖要么目标机自带、要么随包
  • 运行脚本的 LD_LIBRARY_PATH 覆盖了所有随包库
  • 产物没有 RPATH 时，确认运行方式会设置 LD_LIBRARY_PATH

16. 结语

回头看，四个坑各对应一个问题，但难点的性质完全不同：

坑 对应 难在哪
一：sysroot 不完整 Q2 难在排查 —— 报错点离根因很远
二：符号链接被拍平 Q2 难在环境 —— 伪装成编译错误
三：Config 里的宿主路径 Q3 难在排查 —— 路径看起来”很正常”
四：链接成功但库不在 Q4 难在发现 —— 不报错，常规检查全绿

如果只能记住一句话：

交叉编译里，Q1 / Q2 是入门 —— 配好 toolchain file 就能跑通大多数项目。
Q3 是进阶 —— 决定大型项目能不能编出来。
Q4 最容易漏 —— 它不影响编译成功与否，只影响产物能不能跑。

而 Q4 恰恰是最难在构建阶段发现的，因为没有任何自动化检查会告诉你”你链接了一个宿主上的库”。

唯一的办法是老老实实做第三层验收：
